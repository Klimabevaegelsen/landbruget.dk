# Danish Agricultural Database - Table Relationships Guide

> **Purpose**: This document explains how tables in the Landbruget.dk database relate to each other, enabling joins and comprehensive data analysis.

---

## Core Identifiers

The Danish agricultural data system uses standardized identifiers that enable data joining across different government sources:

### CVR Number (Company ID)
- **Format**: Exactly 8 digits (e.g., `12345678`)
- **Purpose**: Uniquely identifies Danish companies
- **Storage**: Varies by table — some store as `VARCHAR/string`, others as `INT32/integer`. Always use `TRY_CAST` when joining across tables with different CVR types.
- **Used in**: `companies`, `field_boundaries`, `field_yearly_data`, `company_pesticide_applications`, `antibiotic_usage`, and many other tables
- **Validation Pattern**: `^\d{8}$`
- **CRITICAL JOIN RULE**: Never use `CAST(cvr AS INTEGER)` — empty strings will crash. Always use:
  ```sql
  -- String CVR → Integer CVR:
  TRY_CAST(string_table.cvr_number AS INTEGER) = int_table.cvr_number
  -- Or cast both to VARCHAR:
  string_table.cvr_number = CAST(int_table.cvr_number AS VARCHAR)
  ```

### CHR Number (Herd ID)
- **Format**: Exactly 6 digits (e.g., `123456`)
- **Purpose**: Uniquely identifies livestock herds/production sites
- **Storage**: String
- **Used in**: `production_sites`, `herd_sizes`, `animal_capacity_log`, `antibiotic_usage`, `vet_events`
- **Validation Pattern**: `^\d{6}$`

### BFE Number (Cadastral Parcel ID)
- **Format**: Variable format (kommune-ejerlav-matr, e.g., `0101-123456-12a`)
- **Purpose**: Uniquely identifies cadastral land parcels
- **Storage**: String
- **Used in**: Property ownership and cadastral data

### Field UUID
- **Format**: UUID (generated deterministically from geometry)
- **Purpose**: Uniquely identifies agricultural fields across years
- **Storage**: UUID
- **Used in**: `field_boundaries`, `field_yearly_data`, `pesticide_applications`, `field_bnbo_areas`, `field_wetland_areas`

### Company UUID
- **Format**: UUID (generated deterministically from CVR number)
- **Purpose**: Internal primary key for companies
- **Storage**: UUID
- **Generated by**: `landbrugsdata_company_uuid(cvr_number)` function
- **Used in**: Most tables as foreign key to `companies` table

## Primary Entity Relationships

### 1. Company-Centric Relationships

The `companies` table is the central hub for company-related data:

```
companies (id, cvr_number, company_name, municipality, address_geom)
    ├─ field_boundaries (company_id) - Fields owned/operated by company
    ├─ field_yearly_data (company_id) - Annual field data
    ├─ production_sites (company_id) - Livestock production locations (CHR sites)
    ├─ company_pesticide_applications (company_id) - Pesticide usage
    ├─ pesticide_applications (company_id) - Field-level pesticide data
    ├─ building_footprints (company_id) - Farm buildings
    ├─ company_leadership (company_id) - Executive information
    ├─ company_owners (company_id) - Ownership structure
    ├─ animal_transports (company_id) - Animal movement records
    ├─ carbon_emission_factors (company_id) - Climate impact data
    ├─ employee_monthly_counts (company_id) - Employment data
    ├─ subsidy_details (company_id) - Government subsidies
    ├─ visa_yearly_counts (company_id) - Foreign worker data
    ├─ worker_yearly_summary (company_id) - Worker statistics
    └─ yearly_financials (company_id) - Financial reports
```

**Key Join Pattern**:
```sql
-- Join companies with their fields
SELECT c.*, fb.*
FROM companies c
JOIN field_boundaries fb ON c.id = fb.company_id;

-- Or using CVR number directly
SELECT c.*, fyd.*
FROM companies c
JOIN field_yearly_data fyd ON c.cvr_number = fyd.cvr_number;
```

### 2. Field-Centric Relationships

Fields are identified by `field_uuid` and connect various agricultural data:

```
field_boundaries (field_uuid, company_id, geom, area_ha, year, municipality)
    ├─ field_yearly_data (field_uuid) - Annual crop and production data
    ├─ pesticide_applications (field_uuid) - Field-level pesticide applications
    ├─ field_bnbo_areas (field_uuid) - Environmental protection status
    └─ field_wetland_areas (field_uuid) - Wetland coverage
```

**Key Join Pattern**:
```sql
-- Get all data for a specific field
SELECT
    fb.field_identifier,
    fb.area_ha,
    fyd.crop_name,
    fyd.year,
    pa.pesticide_name,
    pa.total_burden_score
FROM field_boundaries fb
JOIN field_yearly_data fyd ON fb.field_uuid = fyd.field_uuid
LEFT JOIN pesticide_applications pa ON fb.field_uuid = pa.field_uuid
    AND fyd.year = pa.year;
```

### 3. Livestock Production Site (CHR) Relationships

Production sites (CHR numbers) link livestock-related data:

```
production_sites (chr, company_id, location_geom, main_species_code)
    ├─ herd_sizes (chr_number) - Current animal populations
    ├─ animal_capacity_log (chr) - Historical capacity records
    ├─ antibiotic_usage (chr_number) - Veterinary treatments
    └─ vet_events (chr_number) - Health events and interventions
```

**Key Join Pattern**:
```sql
-- Get company with all their production sites and animals
SELECT
    c.company_name,
    ps.chr,
    ps.site_name,
    hs.species_name,
    hs.count AS animal_count
FROM companies c
JOIN production_sites ps ON c.id = ps.company_id
JOIN herd_sizes hs ON ps.chr = hs.chr_number;
```

## Common Join Scenarios

### Scenario 1: Company's Fields and Pesticide Usage

```sql
-- Find all pesticide applications for a company's fields
SELECT
    c.company_name,
    c.cvr_number,
    fb.field_identifier,
    fb.area_ha,
    pa.pesticide_name,
    pa.application_date,
    pa.total_burden_score
FROM companies c
JOIN field_boundaries fb ON c.id = fb.company_id
JOIN pesticide_applications pa ON fb.field_uuid = pa.field_uuid
WHERE c.cvr_number = '12345678'
  AND pa.year = 2024;
```

### Scenario 2: Livestock and Antibiotic Usage

```sql
-- Find antibiotic usage for a company's production sites
SELECT
    c.company_name,
    ps.chr,
    ps.site_name,
    au.species_code,
    au.year,
    au.add_per_100_dyr_per_dag AS antibiotic_intensity
FROM companies c
JOIN production_sites ps ON c.id = ps.company_id
JOIN antibiotic_usage au ON ps.chr = au.chr_number
WHERE au.year >= 2020
ORDER BY au.add_per_100_dyr_per_dag DESC;
```

### Scenario 3: Geographic Analysis

```sql
-- Find all fields within a geographic area with their pesticide usage
SELECT
    fb.field_identifier,
    fb.municipality,
    ST_Area(fb.geom::geography) / 10000 AS area_ha,
    COUNT(pa.id) AS pesticide_applications,
    SUM(pa.total_burden_score * pa.treated_area_ha) AS total_pesticide_burden
FROM field_boundaries fb
LEFT JOIN pesticide_applications pa ON fb.field_uuid = pa.field_uuid
WHERE ST_Within(
    fb.geom,
    ST_MakeEnvelope(9.0, 55.0, 10.0, 56.0, 4326)
)
GROUP BY fb.field_identifier, fb.municipality, fb.geom;
```

### Scenario 4: Environmental Compliance

```sql
-- Check environmental compliance status for fields
SELECT
    c.company_name,
    fb.field_identifier,
    fb.area_ha,
    fba.bnbo_status,
    fba.action_required_hectares,
    fba.completed_hectares,
    fwa.wetlands_status
FROM companies c
JOIN field_boundaries fb ON c.id = fb.company_id
LEFT JOIN field_bnbo_areas fba ON fb.field_uuid = fba.field_uuid
LEFT JOIN field_wetland_areas fwa ON fb.field_uuid = fwa.field_uuid
WHERE fba.year = 2024 OR fwa.year = 2024;
```

## Data Lineage and Flow

Understanding how data flows through the system (see `docs/DATA_LINEAGE_COMPREHENSIVE.md` for complete details):

### Company Identification Flow
1. **Source**: CVR number from government registries
2. **Processing**: CVR enrichment pipeline generates deterministic UUID
3. **Function**: `landbrugsdata_company_uuid(cvr_number)` → UUID
4. **Usage**: UUID used as primary key and foreign key throughout database

### Field Identification Flow
1. **Source**: Field boundaries from FVM WFS service
2. **Processing**: Geometry used to generate deterministic UUID
3. **Function**: `landbrugsdata_field_uuid(geometry_wkb)` → UUID
4. **Usage**: UUID enables tracking fields across years even if boundaries change slightly

### CHR Site Identification Flow
1. **Source**: CHR number from livestock registry
2. **Processing**: CHR number used directly as primary key
3. **Linking**: CHR sites linked to companies via `company_id` foreign key

## Coordinate Reference Systems (CRS)

**Critical**: All geometry data in the database uses **EPSG:4326 (WGS84)**.

```sql
-- Verify CRS of geometry
SELECT ST_SRID(geom) FROM field_boundaries LIMIT 1;
-- Returns: 4326

-- Check if point is within Denmark
SELECT ST_Within(
    geom,
    ST_MakeEnvelope(7.5, 54.5, 15.5, 58.0, 4326)  -- Denmark bounding box
) FROM field_boundaries;
```

**Geometry Columns**:
- `companies.address_geom` - Point (company headquarters)
- `production_sites.location_geom` - Point (farm location)
- `field_boundaries.geom` - MultiPolygon (field boundaries)
- `building_footprints.geom` - MultiPolygon (building outlines)

## Temporal Joins

Many tables have year-based data requiring temporal joins:

```sql
-- Correct temporal join: Match data from same year
SELECT
    fb.field_identifier,
    fyd.year,
    fyd.crop_name,
    fyd.area_ha AS crop_area,
    pa.pesticide_name
FROM field_boundaries fb
JOIN field_yearly_data fyd ON fb.field_uuid = fyd.field_uuid
LEFT JOIN pesticide_applications pa ON fb.field_uuid = pa.field_uuid
    AND fyd.year = pa.year  -- ← Critical: join on matching year
WHERE fyd.year BETWEEN 2020 AND 2024;
```

**Tables with Temporal Data**:
- `field_yearly_data` - Year-specific crop data
- `pesticide_applications` - Year and date of application
- `field_bnbo_areas` - Environmental status by year
- `antibiotic_usage` - Monthly/yearly usage records
- `animal_capacity_log` - Daily capacity records

## Aggregated Views and Materialized Views

Several materialized views pre-calculate common aggregations:

### Company Summaries
- `company_pesticide_summary` - Pre-aggregated pesticide metrics per company/year
- `environment_summary` - Environmental impact metrics by company/year
- `animal_welfare_summary` - Livestock welfare metrics
- `carbon_summary` - CO2 emissions by company/year

**Usage Pattern**:
```sql
-- Fast query using materialized view
SELECT * FROM company_pesticide_summary
WHERE company_id = '...'
  AND application_year = 2024;

-- Instead of slow aggregation:
-- SELECT company_id, SUM(...), COUNT(...)
-- FROM pesticide_applications GROUP BY...
```

**Note**: Materialized views must be refreshed to show latest data:
```sql
REFRESH MATERIALIZED VIEW company_pesticide_summary;
```

## Missing Data and NULL Handling

### Common NULL Scenarios

1. **Optional Relationships**: Companies may not have all data types
   ```sql
   -- LEFT JOIN for optional data
   SELECT c.company_name, ps.chr
   FROM companies c
   LEFT JOIN production_sites ps ON c.id = ps.company_id;
   ```

2. **Historical Data Gaps**: Not all data available for all years
   ```sql
   -- Check data availability
   SELECT DISTINCT year FROM field_yearly_data ORDER BY year;
   ```

3. **Geographic Data**: Some companies lack geolocation
   ```sql
   SELECT COUNT(*) FROM companies WHERE address_geom IS NULL;
   ```

## Performance Optimization Tips

### Use Indexed Columns
Most join keys are indexed:
- `companies.cvr_number` (indexed)
- `companies.id` (primary key, automatically indexed)
- `field_boundaries.field_uuid` (indexed)
- `field_boundaries.company_id` (indexed)
- `production_sites.chr` (primary key)

### Spatial Queries
Use spatial indexes for geometry operations:
```sql
-- Efficient spatial query
SELECT * FROM field_boundaries
WHERE ST_Intersects(
    geom,
    ST_Buffer(ST_SetSRID(ST_MakePoint(10.0, 55.0), 4326)::geography, 5000)::geometry
);
```

### Materialized Views
For complex aggregations, use existing materialized views when available.

## Data Quality Considerations

1. **CVR Validation**: Always validate CVR numbers are 8 digits
   ```sql
   WHERE cvr_number ~ '^\d{8}$'
   ```

2. **CHR Validation**: Always validate CHR numbers are 6 digits
   ```sql
   WHERE chr_number ~ '^\d{6}$'
   ```

3. **Temporal Consistency**: When joining temporal data, always match on year
   ```sql
   AND table1.year = table2.year
   ```

4. **Geometry Validity**: Check geometry is valid before spatial operations
   ```sql
   WHERE ST_IsValid(geom)
   ```

## Example: Complete Company Profile Query

Here's a comprehensive query that demonstrates multiple join patterns:

```sql
SELECT
    -- Company information
    c.cvr_number,
    c.company_name,
    c.municipality AS company_municipality,

    -- Field data
    COUNT(DISTINCT fb.field_uuid) AS total_fields,
    SUM(fb.area_ha) AS total_farm_area_ha,

    -- Pesticide usage
    COUNT(DISTINCT pa.id) AS pesticide_applications,
    SUM(pa.total_burden_score * pa.treated_area_ha) AS total_pesticide_burden,

    -- Livestock data
    COUNT(DISTINCT ps.chr) AS production_sites,
    SUM(hs.count) AS total_animals,

    -- Financial data
    MAX(yf.revenue) AS latest_revenue

FROM companies c
LEFT JOIN field_boundaries fb ON c.id = fb.company_id
LEFT JOIN pesticide_applications pa ON fb.field_uuid = pa.field_uuid AND pa.year = 2024
LEFT JOIN production_sites ps ON c.id = ps.company_id
LEFT JOIN herd_sizes hs ON ps.chr = hs.chr_number
LEFT JOIN yearly_financials yf ON c.id = yf.company_id AND yf.reporting_year = 2024

WHERE c.cvr_number = '12345678'
GROUP BY c.cvr_number, c.company_name, c.municipality;
```
